# Спека: пилот Onvy в чайхане

**Старт пилота — 31 июля 2026.** На разработку трое суток: 28, 29, 30 июля.
Источник продукта: `Onvy_ Realtime Voice Assistant for Russian Frontline Re.pdf`.
Ревьюер кода — владелец продукта. Обновлено: 2026-07-28.

---

## 1. Цель

Платный пилот в одной чайхане, дающий **измеренные цифры** для инвестраунда:
Δ среднего чека и скорости обслуживания, подтверждённая себестоимость on-premise ASR.

Планка: **пилот = прод в миниатюре**. Тот же стек, та же схема данных, тот же деплой,
что поедут на десятого клиента. Масштабируется количество нод, не архитектура.

## 2. Зафиксированные решения

| Решение | Выбор | Следствие |
|---|---|---|
| Устройство | Личный телефон + проводная гарнитура с кнопкой | PWA, HTTPS обязателен (иначе нет микрофона) |
| ASR | `GigaAM-Multilingual` на арендованной GPU-ноде | **Не** `GigaAM-v3` — та только русская. Ветка `ai-sage/GigaAM-Multilingual` |
| ASR на старте | Адаптер Yandex включён по умолчанию, GigaAM — флагом | Дата 31.07 не зависит от готовности GPU-ноды |
| Перевод | Yandex Translate (облако) | Покрывает все языки включая таджикский; локальный NLLB не тащим |
| TTS | Yandex SpeechKit | Голоса ru/en/uz/kk уже работают в коде |
| Сервер | VPS в РФ (Selectel / Timeweb / reg.ru) | Docker compose + Caddy TLS, данные в РФ |
| Меню | Ручной ввод + импорт CSV | `MenuSourcePort`, адаптер iiko — после пилота |
| Ревью | Человек, после каждого лупа | Мелкие читаемые диффы, агенты не мержат сами |

**Языки пилота.** Полный цикл (распознавание + перевод + озвучка): `ru`, `uz`, `kk`, `ky`, `en`.
Таджикский — деградация: перевод и озвучка есть, распознавание требует ручной проверки
(официального подтверждения таджикского STT у Яндекса не нашли, у GigaAM его нет).

**Архитектурное ограничение (правовое).** Продукт **не идентифицирует человека по голосу**.
Никакого voice-ID, никакой диаризации с привязкой к личности. Голос обрабатывается только
как носитель смысла — транскрибация, перевод, передача. Это выводит пилот из-под режима
биометрических ПДн и ГИС ЕБС. Появление любой функции «узнать, кто говорит» — отдельный
юридический раунд, не в пилоте.

## 4. Роли и группы

| Роль | Голосом | Кабинет |
|---|---|---|
| Официант | Спрашивает про блюдо и стоп-лист, говорит на кухню и в бар | Личный: цели, прогресс |
| Кухня | Принимает и подтверждает реплики зала | Нет |
| Бар | То же по напиткам | Нет |
| Хостес | Broadcast по залу | Нет |
| Управляющий | Слышит всё, ведёт стоп-лист | Полный: стоп-лист, персонал, метрики |

Группы: `зал`, `кухня`, `бар`, `все`. Маршрутизация голосом: «Онви, скажи кухне…».

## 5. Сценарии и приёмка

### S1. Подсказка по меню
«Онви, что в составе лагмана» → ответ голосом на языке сотрудника.
**Приёмка:** ответ строится **только** по данным меню заведения, модель не досочиняет;
блюдо в стоп-листе — говорится первым; p95 от отпускания кнопки до звука ≤ 2.5 с.

### S2. Аллергены (юридически значимый сценарий)
«Онви, есть ли в этом блюде орехи» → ответ по техкарте.
**Приёмка:** если данных об аллергенах по блюду нет — ассистент говорит
«по этому блюду данных нет, уточните на кухне». **Угадывать запрещено.**
Информация об аллергенах и весе порции — требование ЗоЗПП к заведению, цена ошибки
здесь не UX-баг, а ответственность клиента.

### S3. Связь с переводом
Официант говорит на узбекском → повар слышит на своём языке; ответ идёт обратно.
**Приёмка:** доставка ≤ 2 с p95; при отказе перевода доставляется оригинал с явной
пометкой (никогда не тишина); хранится оригинал + перевод.

### S4. Стоп-лист
Управляющий выключает позицию с телефона → следующий запрос уже знает.
**Приёмка:** ≤ 5 секунд действий; видно всем ≤ 3 с; ведётся история изменений.

### S5. Broadcast
«Онви, скажи всем: гости на 12-й стол» → слышат все онлайн в группе.
**Приёмка:** доставка только своей точке и группе; отправитель слышит подтверждение.

### S6. Кабинет управляющего
Кто на смене, история реплик, метрики пилота, латентность стека, выгрузка CSV.

## 6. Нефункциональные требования

- **Латентность S1.** Запись ≤ 0.3 с + ASR ≤ 0.8 с + поиск/LLM ≤ 0.8 с + TTS ≤ 0.6 с.
  Каждая стадия меряется и пишется в лог — эта цифра идёт в отчёт пилота.
- **Чанкинг вместо стриминга.** У GigaAM нет нативного потокового распознавания
  (только сегменты до 25 с). PTT-сценарий это переживает: пишем по кнопке, режем по паузе.
  Непрерывное распознавание на этой модели не проектируем.
- **Деградация.** Падение GPU-ноды не роняет связь: рация работает, ассистент честно
  отвечает «сейчас недоступен». Падение перевода → доставка оригинала с пометкой.
- **Безопасность.** PIN + JWT (короткий access + refresh), роли, WS по одноразовому тикету,
  rate-limit. Сотрудник слышит только свою точку и свою группу.
- **Данные.** Всё в РФ. Сырое аудио — минимальный срок хранения, доступ по ролям.
- **Сеть.** Wi-Fi в зале нестабилен: клиент переживает обрыв WS и переподключается сам.
- **Эргономика.** Кнопка PTT нажимается одной рукой не глядя; экран читается при ярком
  свете и под углом; проверка на 360 px обязательна.

## 7. Правовой гейт (до 31 июля, не блокирует разработку)

Закрыть **до первого включения устройства**:
1. Письменное согласие сотрудника на обработку голоса: цель, перечень действий, срок
   хранения, право отзыва. Явная оговорка: это **не** согласие на биометрическую идентификацию.
2. Допсоглашение к трудовому договору об аудиозаписи на рабочем месте.
3. Актуализация Политики обработки ПДн заведения (новая категория — аудио персонала),
   при необходимости — уведомление РКН.
4. Табличка в зале для гостей: ведётся аудиозапись в целях обслуживания + контакт по ПДн.
5. Технически: retention сырого аудио, шифрование, доступ по ролям, ничего третьим лицам.

Вычитку у юриста по ПДн рекомендую до старта — область менялась в 2025–2026, штрафы
за обработку без согласия измеряются сотнями тысяч, за утечку биометрии — миллионами.

## 8. Архитектура (порты и адаптеры)

```
transport (HTTP/WS) → application (сценарии) → domain → infrastructure (адаптеры)
```

| Порт | Адаптер на пилоте | Потом |
|---|---|---|
| `SpeechRecognitionPort` | Yandex (default) + GigaAM (флагом), карта «язык → провайдер» | GigaAM на все языки |
| `SpeechSynthesisPort` | Yandex SpeechKit | локальный TTS |
| `TranslationPort` | Yandex Translate | локальный NLLB |
| `AnswerPort` | YandexGPT над меню | своя модель |
| `MenuSourcePort` | ручной ввод + CSV | iiko / R-Keeper |
| `EventBusPort` | Redis pub/sub | он же |

Домен не знает ни одного имени вендора. Смена провайдера — новый файл в `infrastructure/`,
ноль правок в домене. У каждого порта есть fake-адаптер для тестов.

`MenuSourcePort` проектируется под реальность POS: состав, аллергены, вес и время отдачи —
**опциональные** поля (заведения часто не заполняют техкарты). Стоп-лист — отдельный,
более «живой» поток с TTL, а не часть статичной номенклатуры; поддерживаются оба режима
обновления — push и polling (R-Keeper умеет только polling).

## 9. Данные

Postgres + Alembic с первого дня. Сущности: `venue`, `employee` (роль, язык, PIN-хеш),
`group`, `menu_item` (состав?, аллергены?, острота?, время отдачи?, вес?, цена),
`stop_list_entry`, `utterance` (оригинал + перевод + метрики стадий), `assistant_query`,
`metric_snapshot`. `venue_id` во всех запросах — мультиточечность заложена сразу.

## 10. Метрики пилота

Схема — **до/после на одной группе**, не A/B внутри точки: в одном зале контроль
загрязняется (официант без устройства спросит коллегу с устройством), а выборка 5–15 человек
не даёт статистической мощности.

- Baseline: 2 недели POS-данных до старта (средний чек, оборачиваемость стола, время отдачи).
- Пилот: 2–4 недели. **Первые 3–5 смен исключаются** из финальных цифр — эффект новизны.
- Фиксировать конфаундеры: не менялись ли меню, цены, состав смены.
- **Скорость реакции на гостя** — метрика, которой у заведения не было в принципе; её даёт
  только Onvy. Сильный аргумент для инвестора, но честно помечаем: источник эффекта и
  источник измерения совпадают, нужна выборочная внешняя проверка наблюдением.

## 11. Не входит в пилот

Voice-ID и распознавание говорящего (правовой периметр), геймификация сверх базовых целей,
обучающие курсы, индор-локация, интеграции с POS, голосовые рассылки HQ, нативные
приложения, биллинг и тарифы, свои гарнитуры, аналитика 100% диалогов.

## 12. Открытые вопросы

1. Таджикский STT — проверить руками до старта, есть ли он у Яндекса.
2. Учётная система чайханы (iiko / R-Keeper / тетрадь) — влияет на приоритет адаптера.
3. Wi-Fi в зале и на кухне — влияет на режим деградации.
4. Кто из персонала на каком языке реально говорит — нужен разговор с управляющим.
