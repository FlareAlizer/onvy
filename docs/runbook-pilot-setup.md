# Runbook: подготовка точки к первой смене пилота

Пошагово — от пустой БД (после `alembic upgrade head`, см. `docs/runbook-deploy.md`)
до розданных PIN-кодов и проверки, что официант слышит кухню. Рассчитан на
управляющего/того, кто физически в чайхане вечером 30 июля.

Инструменты: `scripts/seed_venue.py` (заводит точку, группы связи, персонал,
меню) — работает через `DATABASE_URL` из `.env` сервера, ничего не спрашивает
кроме конфиг-файла. Живая БД для этого шага обязательна: сидинг не работает
"в память", он пишет в ту же Postgres, на которой будет крутиться пилот.

## 0. Перед началом

- Сервер поднят, `alembic upgrade head` прогнан (`docs/runbook-deploy.md`, шаг 3) —
  таблицы `venues`/`employees`/`comm_groups`/`menu_items`/... существуют.
- У вас есть: название чайханы, часовой пояс, список персонала первой смены
  (имя, роль, язык), выгрузка меню в CSV (или готовы завести меню руками позже).
- Роли — ровно эти пять (другие не приняты): `waiter`, `kitchen`, `bar`, `host`, `manager`.
- Языки — ровно эти шесть: `ru`, `uz`, `kk`, `ky`, `en`, `tg` (`tg` — с оговоркой,
  распознавание речи на нём не гарантировано, см. specs/pilot-chaihana.md §2).

## 1. Собрать конфиг точки (`venue.json`)

Один JSON-файл описывает точку и весь персонал. Пример для типичной смены
чайханы (официанты, кухня, бар, хостес, управляющий):

```json
{
  "venue": {
    "name": "Чайхана Шарк",
    "timezone": "Asia/Yekaterinburg",
    "default_language": "ru"
  },
  "staff": [
    {"name": "Азиз",            "role": "waiter",  "language": "uz"},
    {"name": "Марина Петровна", "role": "waiter",  "language": "ru"},
    {"name": "Улугбек",         "role": "kitchen", "language": "uz"},
    {"name": "Бахтиёр",         "role": "kitchen", "language": "tg"},
    {"name": "Сергей",          "role": "bar",     "language": "ru"},
    {"name": "Динара",          "role": "host",    "language": "kk"},
    {"name": "Гульнара",        "role": "manager", "language": "ru"}
  ]
}
```

Правила, которые скрипт проверит сам и честно откажется работать, если что-то
не так (лучше упасть здесь, чем на смене):

- `venue.name` обязателен; `timezone` и `default_language` можно не указывать —
  подставится `Europe/Moscow` и `ru`.
- Роль и язык — только из списков выше, опечатка («officiant», «rus») — ошибка,
  не тихая подстановка ru/waiter по умолчанию.
- Имена персонала не должны повторяться внутри файла (сотрудников различаем по
  имени) — если на смене реально два Азиза, добавьте фамилию или уточнение
  («Азиз официант», «Азиз-повар»).

Сохраните файл на сервере, например `/opt/onvy/venue.json`.

## 2. Завести точку, группы связи и персонал

```bash
cd /opt/onvy
docker compose -f deploy/docker-compose.yml --env-file .env exec api \
  python scripts/seed_venue.py setup --config /app/venue.json
```

(Если `venue.json` кладёте не через volume контейнера, а гоняете скрипт с хоста
с `DATABASE_URL`, указывающим прямо на контейнер Postgres — замените команду на
`uv run python scripts/seed_venue.py setup --config venue.json` из корня репозитория.)

Вывод выглядит так:

```
Точка «Чайхана Шарк» (id=1) — создана.
Группы связи: зал, кухня, бар, все.

PIN-КОДЫ ДЛЯ ПЕРВОЙ СМЕНЫ — раздать лично, не пересылать в общий чат.
Имя                 Роль       Язык   PIN
------------------------------------------
Азиз                 waiter     uz     4821
Марина Петровна       waiter     ru     0937
Улугбек               kitchen    uz     6650
...

venue_id для следующих команд (import-menu и т.д.): 1
```

**Запишите `venue_id`** — он нужен для импорта меню и понадобится тем, кто
настраивает фронтенд/QR-коды входа.

**PIN виден только в этом выводе, один раз.** В базе хранится только хеш —
повторно узнать PIN нельзя, только сбросить и завести заново (админ-функция,
не часть этого runbook). Распечатайте вывод или перепишите от руки сразу же —
не оставляйте терминал открытым на общем экране дольше, чем нужно.

### Если нужно доузнать персонал позже (30 июля вечером, например)

Допишите новых людей в `staff` того же `venue.json` (существующих не трогайте —
скрипт сам их узнает по имени и пропустит, не меняя их PIN) и запустите ту же
команду `setup` ещё раз. Новым — новые PIN в выводе, старым — ничего, их PIN
не меняется. Идемпотентно: повторный запуск не создаёт вторую точку и не плодит
вторую «кухню» среди групп связи.

## 3. Загрузить меню

Два варианта — выберите тот, что реально готов у чайханы:

**A. Меню уже в CSV** (выгрузка из тетради/Excel/POS). Колонки по заголовку,
порядок не важен: `название`, `категория`, `цена`, `состав`, `аллергены`, `вес`,
`время отдачи`, `острота`. Обязательны только `название` и `цена` — остальное
опционально, пустая ячейка честно значит "данных нет" (кроме аллергенов: слово
"нет"/"нету"/"отсутствуют" в ячейке — это подтверждение "аллергенов нет", а не
пропуск). Кодировка UTF-8 или CP1251 (Excel под русской Windows) — определится
сама.

Сначала **план, без записи** — посмотреть, что создастся/обновится/отклонится:

```bash
docker compose -f deploy/docker-compose.yml --env-file .env exec api \
  python scripts/seed_venue.py import-menu --venue-id 1 --csv /app/menu.csv --dry-run
```

Если план выглядит разумно (отклонённых строк нет или они понятны и ожидаемы) —
применить по-настоящему:

```bash
docker compose -f deploy/docker-compose.yml --env-file .env exec api \
  python scripts/seed_venue.py import-menu --venue-id 1 --csv /app/menu.csv
```

Повторный запуск с тем же CSV безопасен: позиции с тем же названием
обновляются (цена/состав/аллергены), а не дублируются.

**B. Меню появится позже.** Пропустите этот шаг — точка и персонал уже готовы
к работе, меню можно довезти в любой момент до 31 июля тем же способом. Пока
меню пусто, ассистент честно отвечает "в меню такого не нашёл" — это ожидаемо,
не баг.

**C. Через кабинет управляющего** (когда фронтенд готов) — то же самое можно
сделать через `POST /api/venues/{venue_id}/menu/import` в вебе, без консоли
сервера. CLI выше — для случая, когда кабинет ещё не развёрнут или нужен
быстрый повтор без интерфейса.

## 4. Раздать PIN-коды

- Раздавайте лично, каждому свой — не общим списком в чат смены (список видит
  почти любой в общем чате, а PIN должен знать только его владелец).
- Предупредите: PIN — 4 цифры, вводится при выборе своего имени на экране
  входа (`/api/auth/venues/{venue_id}/employees` отдаёт список активных
  сотрудников по именам для фронтенда — вводить `employee_id` руками не нужно,
  это делает интерфейс).
- Если сотрудник забыл/потерял PIN — не пытайтесь его "вспомнить", в базе
  только хеш. Заведите его заново той же командой `setup` под новым/уточнённым
  именем, либо дождитесь админ-функции сброса PIN (не в этом runbook).

## 5. Проверить, что официант вошёл и слышит кухню (S3)

Минимальная сквозная проверка перед стартом смены — сделать вдвоём (официант
+ повар) на реальных телефонах/гарнитурах:

1. **Официант** открывает PWA, выбирает своё имя из списка, вводит свой PIN.
   Успешный вход — экран показывает его роль и группы (зал, все).
2. **Повар** делает то же самое на своём устройстве — экран показывает кухня, все.
3. Официант нажимает кнопку и говорит: **«Онви, скажи кухне: гостям нужен ещё
   один комплект приборов»** (на своём языке — если официант говорит по-узбекски,
   так и произносит).
4. У повара в наушнике должен прозвучать перевод на его языке **в пределах
   пары секунд** (бюджет S3 из спеки — доставка ≤2с p95, это не строгий тест
   вживую, а грубая проверка "не подвисло").
5. Повар — тем же способом — отвечает официанту голосом.
6. Официант должен услышать ответ (переведённый на его язык, если языки разные).

Если что-то не сработало:

- **Не приходит вообще** — проверить, что оба устройства реально "на связи"
  (см. `docker compose ... logs -f api`, ищите "на связи" по employee_id из
  логов `app/api/comms.py`); проверить Wi-Fi в зале/на кухне.
- **Пришло, но без перевода** (оригинал с пометкой) — это ожидаемая деградация
  (S3, "при отказе перевода — оригинал с пометкой, не тишина"), проверить
  `YANDEX_API_KEY`/`YANDEX_FOLDER_ID` в `.env` сервера.
- **Тишина совсем** — проверить `/health` (`curl -fsS https://<домен>/health`),
  что `"yandex": "on"`; если `"off"` — речевой стек не настроен, реплики без
  перевода/TTS работать не будут.

Отдельно проверить стоп-лист (S4, займёт минуту): управляющий с телефона
ставит любую позицию меню в стоп через кабинет/API, официант почти сразу
спрашивает у ассистента про эту позицию — ответ должен упомянуть, что блюда
нет, **первым**, до остального ответа.

Если оба шага (S3 и стоп-лист) прошли — точка готова к первой смене.
