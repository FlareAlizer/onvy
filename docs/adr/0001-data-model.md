# ADR 0001 — Модель данных пилота (чайхана)

Дата: 2026-07-28. Статус: принято.
Источник требований: `specs/pilot-chaihana.md` §2, §5–§10.

## Контекст

Демо-версия проекта была ритейл-магазином на SQLite с `Base.metadata.create_all()`
(`app/db.py`, `app/models/*`). Пилот меняет предметную область на общепит
(чайхана) и стек хранения — Postgres 16 + Alembic с первого дня, без
`create_all` в рантайме. Старые файлы удалены полностью (`app/db.py`,
`app/models/`) — это переезд на новую схему, а не миграция данных: сохранять
из демо-БД нечего.

## Решения

**1. Postgres + асинхронный Alembic, без create_all.**
`app/db/engine.py` — один `create_async_engine` (asyncpg), `app/db/session.py`
даёт `get_session()` с явным commit-на-успехе / rollback-на-исключении на
каждый запрос. `alembic/env.py` берёт DSN из `app.config.settings`, а не из
`alembic.ini` (единый источник конфигурации, никаких секретов в файле,
попадающем в репозиторий). Первая миграция (`7430c1b28909_initial_schema.py`)
создаёt всю схему одним файлом — данных для сохранения нет.

**2. `venue_id` во всех доменных таблицах с первого дня**, как явно
зафиксировано в спеке (§9), а не только у сущностей "верхнего уровня" —
это позволяет фильтровать любую таблицу по точке без обязательного join
через `employee`/`menu_item`, что и безопаснее (меньше риска случайно
утечь данные другой точки при неполном join), и быстрее для основных
экранов (лента, стоп-лист, метрики).

**3. Роли и языки — CHECK-констрейнт на VARCHAR, не Postgres ENUM.**
`ALTER TYPE ... ADD VALUE` нельзя выполнить внутри транзакции — это
ловушка именно в разгар пилота, когда набор ролей/языков может
уточниться за одну ночь. CHECK меняется обычным `ALTER TABLE` в одной
транзакционной миграции. Список языков (`ru, uz, kk, ky, en, tg`) и ролей
(`waiter, kitchen, bar, host, manager`) вынесен в `app/db/models/enums.py`,
переиспользуется в `employee`/`venue`/`utterance`.

**4. Техкарта `menu_item` — все поля состава/аллергенов/остроты/веса/времени
отдачи NULLABLE, и NULL сознательно отличается от "пусто".**
Это прямое следствие S2 (спека §5): заведения массово не ведут техкарты,
и ассистент обязан ответить "по этому блюду данных нет" вместо угадывания
— угадывание про аллергены не UX-баг, а юридическая ответственность
заведения по ЗоЗПП. На уровне колонки:
  - `allergens IS NULL` — аллергены не проверялись, ассистент должен
    честно сказать "данных нет, уточните на кухне";
  - `allergens = '{}'` (пустой массив) — кухня явно подтвердила: аллергенов
    нет. Это разные факты, и разница обязана жить в БД, а не только в UI,
    иначе любой клиент API рано или поздно смешает "не знаю" и "нет".
  - то же для `composition`, `spiciness`, `portion_weight_g`,
    `prep_time_minutes`.

**5. Стоп-лист — отдельный поток `stop_list_entries`, не флаг на `menu_item`.**
Явное требование спеки (§8, §9): нужна история (кто поставил, кто снял,
когда) для аналитики пилота, а не только текущее состояние. `unset_at IS
NULL` = позиция сейчас в стопе; частичный индекс
`ix_stop_list_entries_active` по `(venue_id, menu_item_id) WHERE unset_at
IS NULL` — это самый горячий путь ассистента (проверка на каждый вопрос
про блюдо, S4).

**6. `menu_item` не имеет отдельного `is_active`/"нет в наличии сейчас".**
Соблазн продублировать доступность блюда прямо в номенклатуре — тот же
анти-паттерн, от которого явно предостерегает спека для стоп-листа
("живой поток, а не флаг"). Временная недоступность — целиком в
`stop_list_entries`; `deleted_at` (soft-delete) на `menu_item` означает
только окончательное снятие позиции с меню (админ-действие), не "сегодня
закончилось".

**7. Связки через FK-таблицы, а не `ARRAY(Integer)`.**
`assistant_query_menu_items` (какие позиции подтянулись в ответ
ассистента) и `employee_comm_groups` (членство в группе связи) — обычные
таблицы-связки с составным PK и явными FK, а не массивы id. Массив id
не даёт ссылочной целостности на уровне БД (можно сослаться на
несуществующую или уже удалённую позицию), а тут это требование прямо
из custom-инструкций по зоне данных.

**8. FK `ondelete`:**
  - Бизнес-сущности → `venues` (employee, comm_group, menu_item,
    stop_list_entry, utterance, assistant_query, metric_snapshot):
    `ON DELETE RESTRICT`. Точку с живым персоналом/меню/историей нельзя
    удалить одним махом — это должно быть осознанное архивирование
    (`deleted_at`), а не случайный каскад, стирающий историю пилота.
  - Ссылки на `employee` (кто отправил/спросил/поставил в стоп) —
    `RESTRICT` по той же причине: сотрудники не удаляются физически
    (soft-delete), поэтому RESTRICT практически никогда не блокирует
    реальную работу, а лишь защищает от случайного hard delete.
  - `stop_list_entry.menu_item_id` → `menu_items`: `CASCADE`. Позиции
    меню тоже не удаляются физически на практике (soft-delete), поэтому
    каскад — просто защита на случай, если кто-то всё же почистит БД
    руками; исторические записи о конкретном блюде без смысла
    сохранять, если самого блюда в системе больше нет ни в каком виде.
  - `employee_comm_groups`, `assistant_query_menu_items.assistant_query_id`:
    `CASCADE` — чисто связующие таблицы, живут и умирают вместе с
    родителем.
  - `assistant_query_menu_items.menu_item_id`: `RESTRICT` — сохраняет
    целостность истории "что показывали" даже если способ хранения
    меню поменяется.

**9. `metric_snapshot.metrics` — JSONB, а не жёсткие колонки.**
Набор метрик пилота (средний чек, латентность по стадиям p95, доля
неудачных переводов и т.п.) будет уточняться 29–30 июля по факту первых
прогонов. JSONB избавляет от блокирующих миграций в разгар трёхдневного
спринта; типизированы только `venue_id` + `snapshot_date`
(`UNIQUE(venue_id, snapshot_date)` — один снимок на день, повторный расчёт
делает upsert).

**10. Метрики стадий `utterance` vs `assistant_query` называются по-разному.**
У `utterance` три реальные стадии — `asr_ms`, `translate_ms`, `tts_ms` (S3:
распознали → перевели → озвучили другому языку). У `assistant_query` шаг
перевода отсутствует по конструкции сценария (ассистент отвечает сразу на
языке спросившего) — вместо `translate_ms` у него `llm_ms` (поиск/LLM-этап
из бюджета латентности §6: ASR ≤0.8с + поиск/LLM ≤0.8с + TTS ≤0.6с).
Спека §9 говорит "те же метрики стадий" общей фразой — здесь это решение
инженерного толкования: колонки той же формы (мс, nullable), но с именами
по факту реального конвейера, а не искусственно одинаковые.

**11. Мягкое удаление только на бизнес-сущностях.**
`venue`, `employee`, `comm_group`, `menu_item` — `TimestampMixin` +
`SoftDeleteMixin` (`created_at`, `updated_at`, `deleted_at`).
`utterance`, `assistant_query`, `stop_list_entry`, связующие таблицы —
только неизменяемый `created_at`/`set_at`: это лог событий, апдейта у
записи по смыслу не бывает (кроме `unset_at` у `stop_list_entry`, что и
есть единственное разрешённое "изменение" в этой таблице).

**12. `pin_hash` — argon2id, без обратного lookup по PIN.**
Соль в argon2 делает одинаковый PIN у двух сотрудников разными хешами —
поэтому `UNIQUE` на `pin_hash` ничего не гарантирует и не добавлен.
Экран логина показывает список сотрудников точки по имени, сотрудник
выбирает себя и вводит PIN на проверку конкретного хеша — это
ответственность auth-слоя (не входит в зону данных), просто фиксирую
здесь, чтобы никто не пытался класть unique-констрейнт на хеш.

## Правовое ограничение (специально выделено)

По specs/pilot-chaihana.md §2: продукт **не идентифицирует человека по
голосу**. Ни в одной таблице нет и не предполагается:
- слепка/эмбеддинга голоса (voice-ID, спикер-верификация);
- диаризации с привязкой сегмента речи к личности;
- хранения сырого аудио в БД — только текст (`utterance.source_text`,
  `translated_text`) и метрики стадий в миллисекундах.

Если в будущем понадобится всё же хранить аудио (например, для отладки
качества ASR) — только как **ссылку на файл с коротким сроком жизни**
(объектное хранилище + TTL, retention по правовому гейту §7 спеки), не как
BLOB/bytea в Postgres и не в этой ADR-модели. Это отдельный юридический
раунд (биометрические ПДн, ГИС ЕБС), не часть пилота — если кто-то в
будущем добавит такую колонку без пересмотра этого решения, это осознанное
нарушение зафиксированного здесь ограничения.

## Осознанно отложено (не в этом ADR)

- Реальные значения `venues.timezone`/PIN сотрудников — сидинг данных
  чайханы не входит в зону данных (это данные, не схема).
  - `venues.timezone` default = `"Europe/Moscow"` — заглушка, реальный
    часовой пояс точки задаётся при создании строки `venue`.
- Полнотекстовый/fuzzy-поиск по `menu_item.name` (для голосового
  "что в составе лагмана" при неточном произношении) — не в первой
  миграции; если понадобится — `pg_trgm` + GIN-индекс отдельной миграцией
  после того, как будет видно, как реально работает связка ASR → поиск.
- Ролловер/партиционирование `utterances`/`assistant_queries` по времени —
  преждевременно для пилота на одну точку и 2–4 недели; вернуться, если
  объём поставит вопрос о производительности.
- iiko/R-Keeper адаптеры и импорт CSV меню — не про схему `menu_item`,
  а про `MenuSourcePort`/сервисный слой (не зона данных).

## Проверка

`alembic upgrade head` / `alembic downgrade base` проверены **офлайн**
(`alembic upgrade head --sql`, `alembic downgrade <rev>:base --sql` —
генерация SQL без подключения к БД, только компиляция диалектом
postgresql) — синтаксис и порядок операций по зависимостям корректны.

**Не проверено на живом Postgres**: в окружении, где готовилась эта
миграция, нет ни Docker, ни локального `psql`/`postgres` (`which docker`,
`which psql`, `which pg_ctl` — пусто). Реальный прогон `alembic upgrade
head` → `alembic downgrade base` → `alembic upgrade head` против
Postgres 16 нужно выполнить на машине/CI, где Docker или сам Postgres
доступны, до того, как эта схема будет считаться окончательно принятой.
